Pattern: Single-Call (no retrieval, no tools, no chaining) Modes: Simple & Structured

Single-Call Example App

The simplest agentic building block: one prompt goes in, one model response comes out — no retrieval, no external tools, no multi-step chaining. Toggle between a plain-text response and a schema-conforming structured response to see the same pattern rendered both ways.

What is the single-call pattern?

A single call sends one prompt to the shared generation service and returns one response, with nothing in between — no dataset lookup, no external tool, no follow-up call. It's the right choice for straightforward tasks like summarizing, classifying, or extracting information from a piece of text, where grounding in outside data or live information isn't required.

Pattern: Chained Calls (exactly 2 sequential calls) Roles: Struggling Writer → Harsh Critic

Chained-Calls Example App

Submit a short story idea. It's routed through two sequential model calls: a "struggling writer" persona drafts the story, then a "harsh critic" persona critiques that exact draft. Both the intermediate and final outputs stay visible, so the hand-off between steps is never hidden.

What is the chained-calls pattern?

A chained-calls workflow feeds the output of one model call into the input of the next, letting each step focus on a narrower job than a single call could handle alone. Here, Call 1 (the writer) produces a draft, and Call 2 (the critic) receives that draft and produces a critique of it — the second call's input is literally the first call's output.

To conserve shared usage, this demo intentionally runs exactly two chained calls per submission. The pattern itself supports chains of any length — this is a minimal, legible illustration of it, not a limit of the pattern.

Pattern: Planning Agent Scenario: One-day trip planner Limits: 1 planner + 3 executor calls per run · 3 runs per session

Planning-Agent Example App

Give the agent a city and your interests. A planner call decomposes that fuzzy goal into a small, visible plan of discrete steps — web research plus one final synthesis. The plan is shown first; nothing executes until you explicitly give the go-ahead. Then executor calls run the steps in sequence, each result appearing as it completes, ending in a one-day itinerary.

What is the planning-agent pattern?

A planning agent first calls a model to decompose a goal into a plan of discrete steps, then executes those steps one by one — here, research steps that use the shared web search tool, ending in exactly one synthesis step that composes the final itinerary. Because the plan is produced and displayed before execution, you can inspect exactly what the agent intends to do.

To conserve shared usage, each run in this demo is limited to 1 planner call plus up to 3 executor calls, and you get 3 runs per session. Planning agents in general can use any number of steps — these limits are a quota-conservation choice, not a limit of the pattern.

Pattern: Orchestrated Subagents (fan-out / fan-in) Roster: 4 knowledge-only specialists · exactly 2 chosen Limits: 3 model calls per run · 3 runs per session

Orchestrated-Subagents Example App

Ask a question. A coordinating agent picks exactly two of four fixed specialists, writes a distinct brief for each, and shows you that decision before anything is dispatched. On your go-ahead the two specialists run side by side — independently, at the same time — and their answers are then merged into one integrated response, with both source answers kept on screen.

What is the orchestrated-subagents pattern?

Subagents are independent workers. A coordinator decides who should work on what, writes each of them a brief, and — because neither subagent depends on the other's output — they can run at the same time. That's the fan-out. When both finish, a merge step reconciles their answers into one, which is the fan-in.

To conserve shared usage, each run here uses a fixed budget of 3 model calls (1 coordinator + 2 specialists, with the merge folded into the final call) and you get 3 runs per session. The pattern itself supports any number of agents — these limits are a quota-conservation choice, not a property of the pattern.

These specialists are workers under one coordinator's control, not peers negotiating with each other. For the contrasting case — independent parties with private information exchanging messages across a trust boundary — see the Multi-Agent Collaboration Example App.

Pattern: Multi-Agent Collaboration (peer-to-peer) Scenario: Competitive procurement · 1 buyer vs 2 rival sellers Limits: 6 model calls per run · 2 runs per session

Multi-Agent Collaboration Example App

Pick a procurement scenario and say what matters most to you. A buyer agent acting on your behalf runs one negotiation round against two rival seller agents that each hold private constraints the other cannot see. Opening bids and best-and-final bids run concurrently, the buyer counters each seller on a different term, and the award is explained against your stated priorities — then every hidden position is unsealed.

What is the multi-agent collaboration pattern?

In collaboration, agents are peers, not workers. No agent owns the others' reasoning; each has its own goals, its own private information, and communicates only through explicit sender→recipient messages. Contrast this with the Orchestrated-Subagents example, where one coordinator writes the briefs, controls the workers, and sees everything they produce.

The opacity here is enforced in code, not by instruction: each agent is only ever handed the messages addressed to it, so a seller literally has no channel through which to learn the rival's price — even if it asks. The message log below lets you verify that there is no seller-to-seller traffic at all.

Exchanges use the data model and interaction pattern of the A2A collaboration protocol — inspectable agent identity cards, peer task and message objects with an explicit sender and recipient, and work items attached to each message — but without its network transport. A real deployment would add agent discovery over the wire, authenticated endpoints per party, signed messages, and independent hosting for each organisation.

Candidly: all three agents here ship under one owner, so the trust boundary is staged for teaching rather than genuinely cross-organisational. And for a purchase this simple, a peer negotiation between autonomous agents would be over-engineering in a real system — the pattern earns its keep when the parties really are separate and really do hold information the others must not see. Each run consumes a fixed budget of 6 model calls (2 opening bids + 2 counter-offers + 2 final bids; the RFQ is composed without a model call, the award and reveal narration fold into the final call) and you get 2 runs per session. The pattern itself supports any number of agents and rounds.

Each card is what an A2A-style peer publishes about itself. Private constraints are not on the card — they stay sealed until the round ends.

Pattern: Text Embeddings Reference examples: 24 curated texts across 4 categories

Embeddings Example App

Every piece of text below has been converted into a numeric vector by the shared embedding model, then projected into 2D so semantically similar texts land near each other. Add your own word or phrase to see where it falls among them.

What is an embedding?

An embedding is a numeric vector produced by a model such that texts with similar meaning end up with similar vectors. BWS4 uses one shared embedding model across every example app — the same model that scores passages in the RAG app is used here to place text in space, so "joy" lands near "excitement" and far from "database."
